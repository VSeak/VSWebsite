# Sit Start

A personal site for a bouldering coach. Coaches sign in to manage students and write their training plans. Each student signs in to see only their own plans and leave notes on sessions.

## How it's built

- One page (`index.html`: the header and page shell), styled by `styles.css`, run by plain JavaScript in `js/`. No build step. supabase-js v2 comes from jsDelivr, fonts from Google Fonts.
- The JS files are classic `<script>` tags, not modules: they share one global scope, so any file can call any other's functions. They load in the order listed in `index.html`, and `boot()` runs after the last one. Code that runs straight away at load (not inside a function) can only use what earlier files define. Don't declare the same top-level name in two files (a duplicate `const`/`let` stops the second file loading). A new file needs its own `<script>` tag. Never put CSS or JS back inline in `index.html`: styles go in `styles.css`, code in the `js/` file that fits the list below (or a new file if nothing fits).
  - `core.js`: `CONFIG`, page state (`me`, `draft`, `dirty`), helpers (`esc`, `flash`, `ask`, `crumbs`, field errors), pronouns, date formats, `sendLink`.
  - `app.js`: `boot`, `loadMe`, `route`, the leave check and unsaved marks, foldable cards, the unsaved bar, sign-in pages, staff Home (`ADMIN_PAGES`).
  - `users.js`: the Users page and `#/user/<id>` (roles, staff access).
  - `students.js`: the Students list.
  - `cards.js`: shared cards and pieces: coaches, pagers, the Next Session card and Session History, Coaching Status, Goals, Coach Notes.
  - `student-page.js`: `#/student/<id>` (`adminStudent`).
  - `exercises.js`: Exercises & Drills (the master list) and the `#exMenu` name picker.
  - `plan-editor.js`: `#/plan/<id>` for staff (`adminPlan`, `savePlan`).
  - `student-view.js`: plans as students see them, the student home.
  - `notes.js`: plan notes, shared by the student view and the plan editor.
- Backend: Supabase (auth + Postgres). `supabase/schema.sql` creates everything. Setup steps are in `SETUP.md`. `CONFIG` at the top of `js/core.js` holds the project URL and publishable key.
- **Security is in the database, not the page.** Row-level security in `schema.sql` decides what each user can read or write. Any new table needs RLS and policies. The page never holds the secret key.
- Serve it over http (`npx serve .`), since sign-in links need a real address.

## Accounts

- Staff = a row in `public.staff` (matched by the signed-in email) with `roles`, a set of separate roles: `coach` (students, plans, goals, notes) and `admin` (the Users page: every user, staff and students). One person can have both. `my_roles()` returns them; RLS uses `is_coach()` and `is_admin()`. Admins can edit students' rows (details, invites) but not plans or goals. The `keep_an_admin` trigger refuses any change that leaves no admin, and the page won't let you remove your own Admin role. One staff member is the **owner** (`staff.owner`, set only in the SQL Editor): the `protect_owner` trigger stops anyone else changing their roles or email or removing them, and the owner always keeps Admin. The page locks their roles and hides Remove Access for other admins. To add a role: allow it in the `staff.roles` check, then add it to `ROLE_LABEL`, `ROLE_PLURAL`, `ROLE_HINT` and `STAFF_ROLES`.
- **Coach ownership:** every coach reads every student, but only a student's current coach changes them: plans, sessions, goals, details, next session, coaching status, invite, and replies to their plan notes (`can_coach(student)`, plus `can_coach_plan` / `can_coach_session`, in the RLS policies). A student with no coach can be changed by any coach. Other coaches get a read-only student page (an alert says who coaches them) and a read-only plan, but can add Coach Notes (editing only their own; the student's coach edits any) and add past sessions (only the coach or an admin deletes them). The page mirrors this with `canCoach(s)`. The Students list has My Students, No Coach (only when there are some), Other Coaches' Students (with "Coached by", names from `coach_list()`, since coaches can't read other staff rows) and Inactive; warn tags and Latest Student Notes cover only students you can change. The home tile counts your own active students. `check_student_coach` also fires on `training_ended_at`: End Coaching sets the coach to none (and stamps the server time), and Resume Coaching gives the student back only to the coach they had when it ended, if that coach is the one resuming; anyone else leaves them with no coach for an admin to pick. Otherwise End then Resume would let a coach take a No Coach or another coach's inactive student (`endedCoach()` mirrors it for the hint).
- **Staff who are also students:** a staff member gets a student row with the same email (the Student checkbox under Roles in Add User's Staff mode and on a staff member's `#/user/<id>`; once ticked it stays ticked with a link to the student record, and removing it is Delete Student on that record). `loadMe` always runs `claim_student()`, so `me.student` is set for them too, and the home page gets a **View My Training** tile (`#/me`, the student home under a "My Training" heading, without Your Pronouns). `route()` sends their own `#/student/<id>` to `#/me` and `adminPlan` shows their own plan as the student sees it (`isSelf`). Nobody can be their own coach (`check_student_coach`; the coach picker leaves them out), `is_self()` keeps Coach Notes about themselves hidden from them, and plan notes they post on their own plan are student notes (`notesCtx.coach` decides `from_coach`, not the role). Changing the staff email in the invite form changes the student email too.
- Staff are added on the Users page (the Add User dialog in Staff mode sends the invite straight away). Its Staff / Student switch (`#addKind`) lets an admin add a student too: Student mode hides and disables the email and roles and inserts just a `students` row (name, pronouns). A coach adder becomes their coach (`check_student_coach`) and goes to `#/student/<id>`; an admin-only adder goes to `#/user/<id>` to pick the coach. The invite still waits for a plan and a goal. Staff who leave are **deactivated**, not deleted: the Staff Access card on `#/user/<id>` (hidden on your own page and the owner's) has Deactivate, which sets `staff.deactivated_at`. They keep their row, login and history. `my_roles()`, `is_coach()` and `is_admin()` ignore them, and the `staff_deactivated` trigger deletes their `auth.sessions` (unless the login is also a student's). Their password still works on purpose: `loadMe` spots a deactivated staff row after sign-in, signs them out everywhere, and the sign-in page shows an "Account Deactivated" popup (`deactivatedNotice`; `ask()` with `cancel: false`). Only after a valid password, so guessing an email never reveals the account (a Supabase ban was rejected for that reason: it answers before checking the password). `gate_signup` refuses a deactivated staff email with no login yet. The trigger also leaves their students with no coach and refuses deactivating yourself; `protect_owner` refuses deactivating the owner; `keep_an_admin` counts active admins only. Reactivate clears it (students don't come back). The Users list tags them Deactivated, sorts them last, and has a Deactivated Staff filter (the role filters leave them out). Inactive students (coaching ended) get the same treatment: an Inactive tag, sorted last (before deactivated staff), and an Inactive Students filter; `adminUsers` reads `training_ended_at` from `students`, since `list_users()` doesn't return it. Only a deactivated staff member has Delete Staff: `delete_staff()` (which refuses anyone still active) removes the row and their login (kept if they are also a student). Staff invites pass `staff: true` in the login's data, and both emails switch to staff wording with `{{ if .Data.staff }}`. Staff emails sign off "Welcome aboard!" (invite) or "Thanks for being on the team!" (sign-in link) instead of "Happy training!". Both emails are signed with the first name of the coach or admin who sent them (`{{ .Data.sent_by }}`, or "Sit Start" if it is missing): `sendLink` passes it as data for a new login and first calls `stamp_sender()`, which writes the caller's own staff first name onto an existing login, since Supabase ignores data for a login that already exists.
- Students are added by name first (`email` and `invited_at` start empty), so the coach can build their plan before inviting. The Account card on the student page saves the email, calls `signInWithOtp` to email a link, then sets `invited_at`. The invite waits until the student has a saved plan (one with a title) and a goal: `gateInvite()` disables the button and says what is missing. The student page checks its own data (and re-checks as goals change); the Users page asks `student_ready()`, since admins can't read plans or goals. Until the invite goes out, the Account card (`accountCardStart`, on both `#/student/<id>` and `#/user/<id>`) is the warn color with a Not Invited tag and a warn box. Once a student has signed in, an admin changes their email with Change Email on `#/user/<id>` (an `ask()` dialog), through `change_student_email()`, which also changes their login's email at once (and refuses one a staff member or another login has). The OLD address gets a notice (never the new one), saying to contact their coach or an admin if it's a mistake. It goes out first, while the old address still has a login: `prepare_email_change()` checks the new email and stamps `email_changed_to` (and `sent_by`) on the login and returns the old email, the page sends it the Magic Link email (its `{{ if .Data.email_changed_to }}` wording, no sign-in button), and only then changes the email. If the notice doesn't send, nothing changes. `stamp_sender()` clears `email_changed_to` before any normal link. Before they sign in, the invite form changes it. The list shows Not Invited, Invited or Active. The `gate_signup` trigger on `auth.users` refuses any sign-up whose email isn't in `students` or `staff`, so sign-ups can stay enabled.
- **Delete Student** is only on the Coaching Status card of an inactive student (End Coaching is the archive; delete is for someone added by mistake), and `delete_student()` refuses a student still being coached. It removes the row and the matching `auth.users` login (never a staff member's). Without that, re-adding the email would find the old login: Supabase sends the Magic Link email instead of Confirm signup, and the old password stays.
- Staff send sign-in links (the invite, or Send Sign-In Link). Anyone can also tap **Forgot Password?** on the sign-in page (`forgotPassword`): an `ask()` dialog takes the email and calls `resetPasswordForEmail`, which sends the Reset Password email (`supabase/emails/reset-password.html`, signed "Sit Start") and leads to "Choose a Password" through `PASSWORD_RECOVERY` / `?setpw=1`. Supabase sends nothing for an email with no login but answers the same way, and the page always says "If … has an account, a link is on its way", so it never reveals whether an email has an account (the same reason as the deactivated-staff check). A deactivated staff member who resets still gets the Account Deactivated popup after the link.
- Links go through `mailer`, a second client with no stored session, so sending one never touches the coach's session. Both clients use the implicit flow, so a link works on any device.
- Links redirect to `CONFIG.siteUrl` (the live site, so links sent from localhost still work on a phone), or the current address if it is empty, plus `?setpw=1`. After sign-in, `claim_student()` links the account to the student row (`students.user_id`). A student without `user_metadata.password_set` is sent to "Choose a Password".

## Data

- `staff(id, email, first_name, last_name, name, pronouns, roles, invited_at, owner, deactivated_at)`: `roles` is a text array (`{admin,coach}`, at least one). Admins can read every row; other staff only their own (for the home page greeting). The Users page reads everyone through `list_users()`, which adds `last_sign_in_at` from `auth.users` for the Active status, `owner` and `deactivated_at`.
- `students(id, first_name, last_name, name, pronouns, email, invited_at, user_id, coach_id)`: `name` is generated from first + last (read it for display; write the two parts). First and last are separate so a first name with a space greets correctly. `email` is null until the coach adds it. `coach_id` is their current coach (a staff member with the Coach role, or none). `next_date`, `next_start`, `next_end`, `next_location` are their next training session: all four set (end after start) or all null (`next_session_whole` check). Coaches and admins set it in the Next Session part of the Sessions card on `#/student/<id>` and `#/user/<id>` (`sessionsCardHTML`, `bindSessions`); students can only read their own row, so they just see it at the top of their home page (`nextSessionAlert`) until it ends (date + end time, `nextPassed`). The page keeps the date to today or later. Once it has ended (`nextOverdue`), the card turns the warn color with a Needs Update tag and banner, and the Students list tags the student Update Next Session. `training_ended_at` is null while they are being coached; the Coaching Status card on both pages (`trainingCardHTML`, `bindTraining`) has End Coaching (which also clears the next session and the coach, and makes their current plan a past plan in `check_student_coach`, so it works for admins too) and Resume Coaching (plans stay past; the coach picks one to make current). The code and column keep the old "training" names. An inactive student's Sessions card has only Session History, and they have an Inactive tag by their name. The Students list groups them (see Coach ownership), each card with its count; students you can change are tagged Not Invited or Invited until they sign in. The home tile counts your own active students. Inactive students can still sign in and keep their plans, goals and notes.
- `session_history(id, student_id, session_date, start_time, end_time, location, created_at)`: past sessions, unique per student, day and start time. Staff read it, any coach (not about themselves) or admin adds, and the student's coach or an admin changes or deletes (see Coach ownership); a student reads their own. The page logs an ended Next Session (`logEnded`, an upsert that ignores duplicates) just before anyone updates or clears it, including End Coaching. The page does it, not a trigger, because "ended" depends on the local time. Until then `historyOf()` shows the ended next session as the newest past session anyway. Session History, under Next Session in the Sessions card, shows 3 per page (`HISTORY_PAGE`) with a count ("8 sessions since Aug 2026"), + Add Past Session (an `ask()` dialog; End Time's `min` follows Start Time) and Delete on every row. Deleting an ended Next Session that isn't logged yet clears the next session without logging it. On `#/student/<id>` a row with Coach Notes from that day has a Notes (n) button (`showCoachNotes`: Sessions filter, the page with that day's first note, scrolled to, and every note from that day lit up; `cnoteAt.spot` lights the rest when paging on, until the filter changes or a note is added); a row with none has Add Notes instead (`startCoachNote`: that day becomes the Coach Notes form's filled-in Session Date through `cnoteAt.day`, like picking a missing session, and the Notes box is focused, left as it was). Students see a Your Sessions card on their home page (`studentHistory`), hidden until they have one.
- **Pronouns** (`pronouns` on `staff` and `students`, e.g. `she/her`, empty = not set, at most 40 characters): coaches set a student's on `#/student/<id>`, admins anyone's on `#/user/<id>`, and both Add forms ask. `pronounsField()` is a pick of `PRONOUNS` plus Other with a box to type them; `readPronouns()` reads it back. `pronounsTag()` shows them after the name, smaller and grayed (page headings, Students and Users lists). A student changes only their own pronouns, never their name (so the coach always knows who they are), in the Your Pronouns card at the bottom of their home page, through `update_my_pronouns()`. Text about a person uses `pro(pronouns)`: `p.they`, `p.them`, `p.their` (capitalized `p.They`, `p.Their`) and `p.v(plural, singular)` for the verb, from the first pronoun (she/they → she); anything else, or none, uses they/them.
- `plans(id, student_id, title, overview, start_date, repeats, active)`: `repeats` = Repeat Weekly (the default for new plans): one week of sessions, all week 1, done every week. `false` = Week by Week (week 1, week 2, ... with dates from the start date). `active` = current plan. A student has at most one: the `one_current_plan` trigger turns their other current plan into a past plan (a unique index backs it up), and none is allowed. Plan tags (`planTag`): Current, Past, or Inactive for a non-current plan with no start date. New and copied plans are current only if the student has none yet. A student with a current plan sees it straight away.
- `sessions(id, plan_id, week, position, title, details, exercises)`: `exercises` is JSON `[{name, sets, reps, rest, notes}]`.
- `goals(id, student_id, body, status, done_at)`: `status` is `current`, `achieved` or `archived`; `done_at` is the day (a `date`, no time) it left `current`. The coach adds, edits, marks achieved (Edit Date changes an achieved goal's day), archives, restores and deletes them on the student page (the Goals card re-renders in place). Students see current goals at the top of their home page and a Goals Achieved card at the bottom; RLS hides archived goals from them.
- Coaches: the `check_student_coach` trigger gives a new student the coach who added them (not themselves), clears the coach and current plan on End Coaching and gives the student back to the coach they had then if that coach resumes (their `student_coaches.ended_at` within 5 minutes of `training_ended_at`), refuses a coach change from anyone but an admin (the SQL Editor can too) and only allows staff with the Coach role. `log_student_coach` keeps `student_coaches(student_id, staff_id, coach_name, started_at, ended_at)`, one row per student and coach: the old coach gets `ended_at`, and a returning coach gets their row back (dates reset), so nobody shows as both current and past. `coach_name` keeps a removed coach's name; `delete_staff()` ends their time as coach and `coach_id` goes to null. The table has RLS and no policies: everyone reads it through `coaches_of(student_id)` (staff, or that student), since students can't read `staff`. Existing students started with no coach.
- `notes(id, session_id, author_id, from_coach, author_name, body)`: `author_id` becomes null if the login is deleted (the note stays). Students can add and delete their own. Every coach reads them; only the student's coach replies or deletes. A coach's reply shows their name: the `stamp_note_author` trigger writes `author_name` on insert from the poster's own staff row (students can't read `staff`), keeps it fixed on update, and leaves it empty on student notes. The page falls back to "Coach" if it is empty. Plan notes (`notesHTML`) look like text messages: the reader's own notes (`author_id` = the signed-in user) are bubbles on the right, everyone else's on the left.
- `coach_notes(id, student_id, author_id, author_name, session_date, body, created_at, edited_at)`: Coach Notes, private notes a coach keeps on a student. Only staff with the Coach role have a policy (any coach adds; the author or the student's coach edits or deletes; never about yourself); students and admin-only staff can't see them. A `session_date` makes it notes from that session; empty is a general note. The `stamp_coach_note` trigger sets the author and `author_name` on insert, keeps them (and `created_at`) fixed on update, and sets `edited_at` when the text or date changes. The Coach Notes card on `#/student/<id>` (`coachNotesHTML`, `renderCoachNotes`) re-renders in place, has an All / Sessions / General filter (`.seg`, outside the form so it isn't an unsaved edit), shows 3 notes per page (`CNOTES_PAGE`) with the pager under a Notes / Actions head (laid out like the Master Exercise List), newest first by session day (or the day written). `cnoteMissing` lists past sessions (`historyOf`: Session History plus an ended Next Session) with no note on their date: every one newer than the newest session that has a note, so older backfilled sessions stop counting once a newer one is noted (the user chose this). While any are missing, the card turns the warn color (`.overdue`, like the Sessions card) with a Needs Note tag and a warn box, and the Session Date starts filled in with the newest one's date. With more than one, the warn box has a button per session; picking one (`cnoteAt.day`) makes its date the filled-in one. The buttons all look the same (the Session Date field shows which one is picked; a highlighted one read as a stray color). It lists the newest 3 (`CNOTE_MISSING_SHOWN`) and an And n More button that shows the rest (`cnoteAt.allMissing`); it becomes Show Fewer, which goes back to 3. Not once coaching has ended. The card redraws when the sessions change (`hist.changed`), and a filled-in date follows the prompt unless the coach changed it. It is the field's starting value, so the card isn't marked unsaved until the coach types (a button that changed the field marked it unsaved, which felt wrong).
- `exercises(id, name, name_key, sets, reps, rest, notes, purposes)`: the Master Exercise List. Coaches and admins can do everything; students have no policy, so they can't see it. `name_key` is generated (`lower(trim(name))`) and unique, so names don't repeat ignoring case. Plans copy the values, so editing a plan never changes the list and editing the list never changes a plan. `purposes` (text array, at most 12, `EX_PURPOSES_MAX`) says what an exercise is for, only for coaches to search: plans don't copy it, so students never see it. The form has a pill per purpose to tick. The purposes to pick are `exercise_purposes(id, name, name_key)` rows (same policy as `exercises`; `name_key` unique, at most 40 characters), added, renamed and deleted in the Purposes card under Add Exercise (foldable, starts folded: it alone sits in `data-folds="exercises"`; 5 per page, `PUR_PAGE`, A to Z with Previous / Next), which shows how many exercises use each. The `sync_exercise_purpose` trigger renames a purpose on every exercise, or takes a deleted one off, and the page mirrors it (`redrawPicks` keeps what is ticked in the Add form). The All Exercises card's search matches names and purposes, and a purpose filter (purposes in use, with counts) sits beside it.

## Pages (hash routes, `route()`)

- The staff pages follow design D ("Your Picks") on the Coach & Admin page of the "Sit Start Student Redesign" Claude Design canvas: big 800 headings, 22px cards, filter tabs with counts (`.tabs`, the same buttons as a plan's session tabs), people as cards (`a.person`, `.ini` badge, `.chips`), page actions as a filled button beside the heading (`.page-head`, `.fill`), and rarely used cards joined into one list (`.card-group`, each folded to its heading and a `.fold-sum` summary).
- Staff: `#/` Home (`adminHome`), headed "Welcome <first name>," then "n things need you." or "you're all caught up." (`.hey`). A dark **Needs You** card (`homeNeeds`) lists your own active students whose next session has ended (Update Next Session) or whose past sessions have no Coach Note (Needs Note, `cnoteMissing`), and for admins active students with no coach (Pick a Coach, to `#/user/<id>`). Student notes never show there: replying is up to the coach (the user chose this). With nothing to do, the card says so and shows **Coming Up** (your students' next sessions, `COMING_UP`); coaching nobody, it says so with + Add Student. Admin-only staff with nothing to do get no card. Beside it, one tile per page from `ADMIN_PAGES` with a big number (`stat()`), shown to anyone with one of its `roles` (add a new page there and in `route()`, which also checks the role). Coach and admin: `#/exercises` **Exercises & Drills** (renamed from Master Exercise List; code and table still say exercises): search, purpose tabs (the first `EX_TABS`, then +n More), cards with the student's three boxes, Edit (a dialog) and Delete, 10 per page (`EX_PAGE`, two a row on wide screens), A to Z with Previous / Next; adding or editing goes to the page with that exercise. The Add Exercise form sits beside the list; on a phone it hides behind + Add Exercise at the top (`.only-phone`), which moves it under the heading and opens it. Coach pages: `#/students` filter tabs Mine / No Coach (only when there are some) / Others / Inactive (`studentsTab` keeps the pick), student cards with chips (Update Next Session, Not Invited / Invited, Needs a Plan, Next: day, Coached by), Latest Student Notes beside them, and + Add Student (a dialog); `#/student/<id>`: a status line and the student's counts (Sessions / Goals / Notes) by the name; left, the current plan (Open Plan, + New Plan, Other Plans in a `details`), Student Notes (all of that student's notes, newest first, `noteFeedItem` as text-message bubbles, shared with the Students list; the whole note is one link, `#/plan/<id>/<session id>`, and `openNotes` opens that session's notes, scrolls to them and focuses the reply box) and Coach Notes (amber `.overdue` when a note is missing); right, the dark Next Session card (`nextCardHTML`: coming up, ended and struck through, or not set; Set Next Session / Change open a dialog, `nextSessionFields`), the green Goals card (`.goals-card`), then the card group: Session History (`historyCardHTML`), Coaching Status, Details, Coach (read-only), Account. Plans (other than the current one), Student Notes and each Goals group (current, achieved, archived) show 3 per page (`PLANS_PAGE`, `SNOTES_PAGE`, `GOALS_PAGE`, `pagedBox`); current goals are oldest first, so their pager says Previous and Next. On a phone (`.phone-order`) it's one list: next session, goals, plan, student notes, coach notes, then the group (the D drawing put Next Session first, replacing the old "after Notes" order); `#/plan/<id>` plan editor. Admin pages: `#/users` search, tabs Everyone / Admins / Coaches / Students (Inactive and Deactivated only when there are some; `usersTab`), user cards (`userCard`: deactivated staff grayed out), + Add User (`addUserDialog`: Staff or Student in a dialog; staff need a role, so the first role box stays invalid until one is ticked), and **Waiting on an Admin** (active students with no coach, each with Pick Coach; above the search on a phone); `#/user/<id>`: staff get a Roles card (its own form, Save Roles; ticking Student makes the student row) and their students; a student with no coach opens on an amber **Pick a Coach** card (the coach form), then their Next Session card; the rest (Student Page link for coaches, Session History, Coach, Coaching Status, Details, Account, Staff Access) is the card group.
- Every page below Home starts with `crumbs()`: a **‹ Back** button to the page one level up, then the full trail from Home (no ‹ inside the trail; the user asked). Both change the hash, so the leave check still runs.
- **Leave check:** `unsaved()` is true when the plan editor is `dirty` or any form field on the page differs from how it was drawn (pages redraw their forms after a save). `okToLeave()` asks before a page change (`onHashChange`), Sign Out and New Plan; `beforeunload` covers closing or reloading. After a save, add or delete that moves to another page, navigate with `goTo()`, which skips the check. A redraw of the same page after a save (`adminUser(id, form)`, `adminStudent(id, form)`) keeps unsaved edits in the other forms (`keepEdits`), and the Goals card keeps a goal being typed.
- **Unsaved marks** (made for phones, which have no hover): a form with `data-save` (every Save and + Add form on staff pages, e.g. a goal typed but not added) marks itself and its card `.unsaved` while `fieldChanged` finds a changed field (`markUnsaved`, run on input and reset and, through a MutationObserver, after any redraw). A new `data-save` form's card needs an `h2` (the tag and the bar's name come from it). The card gets a warn edge and an Unsaved tag after its `h2`, and its Save button is filled in. `#unsavedBar` at the bottom of the screen names unsaved cards whose Save buttons are out of view, with Show and, for one card, its Save button (`placeBar`). It hides while the keyboard is up on a touch screen (`body.typing`: a focused field and a visible height well under `fullHeight`, since Android's Back button closes the keyboard but keeps focus). The invite form is `data-save="show"`, since its button sends an email. The plan editor's `.savebar` sits beside the plan's title and gets `.unsaved` while `dirty`: then it turns dark and floats at the bottom right on wider screens, and is fixed across the bottom under 600px, like `#unsavedBar`, where it also hides while typing.
- **Foldable cards:** every card inside an element with `data-folds="<page>"` (the student page `student`, a user's page `user` and the Purposes card, `exercises`) folds down to its heading row when the heading is tapped. `applyFolds()` (run with `markUnsaved` after any redraw) wraps each heading in a `button.fold` for the keyboard and restores which ones are folded. That is stored by heading text (or the card's `data-fold`, for a heading that changes, like "Active (3)" or "Her Students") in `localStorage` (`coaching.folded.<page>`, heading → true for folded, false for unfolded), so a card folded on one student stays folded on all. Cards that are rarely touched have `data-fold-start` and start folded until unfolded once: Session History, Details, Coach, Coaching Status, Staff Access, and Account once the person has signed in (before that it holds the invite, so it starts open). Pick a Coach, Roles and Their Students stay open. Fields stay in the page, so the leave check and Unsaved tag still work. The unsaved bar counts a folded card by its heading and unfolds it on Show or Save.
- **Pages:** a long list shows a few items at a time with `pageOf()`, `pagerHTML()` (‹ Newer, Page n of m, Older ›) and `bindPager()`, which keeps the pager where it was on screen and keeps the focus. Changing a filter goes back to page 1; adding goes to the page with the new item.
- A card's description (`.hint`) goes right under its heading, not at the bottom. Hints about one field stay by that field.
- Student: `#/` "Hey <first name>, let's climb." (`myTop`), then `stuGrid`: the plan (`planReadHTML`) and Past Plans on the left; the next session (a dark card with Today / Tomorrow / In n days), current goals (a green card; several get a count and one line each), Goals Achieved, Your Sessions (headed by the count), Your Coach (current and past, hidden until they have had one) and Your Pronouns on the right. Under 860px it is one column (`display: contents`, `order` in styles.css): next session, goals, plan, past plans, then the rest. `#/plan/<id>` one plan on its own. A plan shows "Current Plan · Repeats Weekly" (or Past / Inactive, Week by Week) over its title; a week with more than one session gets tabs (`data-tab`, `showSession`), one session at a time, and `openNotes` switches to the right one. Notes open from a big button at the bottom of each session.
- The plan editor keeps a `draft` and saves on **Save Plan** (upserts sessions, deletes removed ones). Saving needs a title, a start date and at least one session. New plans start with an empty title (lists show "Untitled Plan" until it is saved). Session ids are made in the browser so notes stay attached. `dirty` feeds the leave check. **Student View** previews the draft. Sessions are tabs like the student's (`weekSessionsHTML`, one session shown at a time, `draft.tab` remembers each week's pick, + Add Session is the last tab); Move Earlier / Move Later only show where a session can go. Each exercise is a small card (`exEditHTML`: name, Sets / Reps/Time / Rest, notes) with Move Up / Move Down (only where it can go) and Remove (a × looked like clearing a field). Plan Details sits beside the sessions (above them on a phone): the Repeat Weekly / Week by Week switch (`.seg`, staff only), title, start date, Current Plan and overview; Repeat Weekly hides the Week field and + Add Week and shows one "Every Week" section. Switching to it (`setRepeats`) keeps only the first week, after asking if later weeks would go. **Duplicate Training Plan** (by Delete Plan, `duplicatePlan`) copies the saved plan for the same student as "<title> (Copy)", with new session ids and no notes, current only if the student has none, and opens it; with unsaved changes (or a plan never saved) it asks to save first. Students just see the result: no week heading for a repeating plan, or Week 1, Week 2, .... Note feeds name the session instead of the week for a repeating plan.
- Exercise names pick from the master list (`draft.library`) through `#exMenu`, a styled dropdown built in the page (not a `<datalist>`, whose popup looks like browser autofill). It shows names containing the typed text, with arrow keys, Enter and Escape. Typing or picking a listed name fills in its sets, reps, rest and notes (`setExName`). `filledFrom` remembers which name the values came from, so fixing a typo in the name doesn't wipe the coach's own values. The picker also matches purposes (typing one lists its exercises) and shows them under each name (a Find Exercises by Purpose select was tried and removed: the user found typing enough). Purposes only show in the editor: plans never copy them. Save Plan then calls `addToMasterList()`, which adds names not on the list yet with the plan's values (upsert on `name_key`, ignoring ones that exist).

## Conventions

- Colors are tokens on `:root`, with dark mode under `prefers-color-scheme` and `[data-theme]`. Don't hard-code colors.
- Look: muted "moss and bark" colors (moss green accent on warm sand/bark neutrals). Fonts: Bricolage Grotesque for headings (800 for the big student-page ones), DM Sans for body text (the user disliked Inter), Sora for the brand in the header (`CONFIG.siteName` on one line). The header is the page color with a line under it and a filled sand Sign Out. These colors are Sit Start's own; other vsapps apps get their own. The student pages (design D) and the staff pages (Coach & Admin page, design D "Your Picks") were designed on a Claude Design canvas ("Sit Start Student Redesign").
- Logo: a jagged boulder with a deep cave on the left (the overhang you sit start under) and a small crash pad inside the cave, no ring. It is inline SVG in the header (and on the root home page card) using `currentColor`, and `icon.svg` is the favicon (moss, lighter in dark mode). `apple-touch-icon.png` (180px, light mark on moss) is for phone home screens; it and `email-badge.png` are drawn with PowerShell System.Drawing from the same points as the SVG path, so redraw both if the mark changes. `email-badge.png` (96px, moss on transparent, shown at 32px) is the badge in both emails, loaded from the live site since email apps don't show SVG; the emails use the same colors as hex values. The three emails in `supabase/emails/` follow design B on the canvas's Emails page: a big "Hey <first name>," greeting with a moss second line above the card, the same fonts as the student pages (falling back to Arial), and the sender's name signed in moss. They are pasted into Supabase by hand, so a change needs a re-paste.
- Must work at phone width (~400px). Students see exercises as cards (`exCardHTML`: name, then Sets / Reps/Time / Rest in three equal centered boxes, "—" when empty, long text wraps inside its box without splitting words that fit (`overflow-wrap: break-word`), then notes); always one card a row, so the order is plain (two a row squeezed the boxes and hid the order). The coach's plan editor keeps its own rows.
- Buttons, headings and labels use title case; hints and messages use sentence case.
- Confirmations use `ask()` (one `<dialog>`), which settles on submit.
